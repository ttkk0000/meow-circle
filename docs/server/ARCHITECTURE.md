## 选择

采用模块化单体：一个 Go 服务进程、一套 PostgreSQL，Redis 可选。业务模块按身份账号、社区关系、私信群聊、宠物与领养、寻宠、预约披露、媒体与审核划分。暂不引入 Kubernetes、服务注册中心、消息集群、跨服务 RPC 或分布式事务。

| 层 | 入口 | 边界 |
|---|---|---|
| HTTP | `internal/platform/mobileapi` | DTO 解码、会话、操作员入口、错误与状态码；不能任意写数据记录 |
| 身份 | `internal/identity` | 验证码、绑定、账号资料、单次授权、会话轮换与撤销；SMS/OAuth 通过端口接入 |
| 业务 | `internal/mobile` | 各功能文件中的命令、可见性、状态机与快照；不依赖 HTTP、SQL、Redis、第三方 SDK |
| 持久化端口 | `mobile.Repository / Tx` | 带 context、错误、事务和版本的存取；不沿用旧 Store 的 bool/零值吞错 |
| 适配器 | `internal/store/mobile.go`、`postgres/mobile.go` | 内存回滚模拟；PostgreSQL 可串行化写事务、CAS、唯一键与索引 |
| 外部系统 | `internal/platform/mobileauth` | HTTPS SMS 网关、微信/QQ 校验、Apple 授权码交换/签名/nonce/撤销 |

`mobile.Service` 是进程内业务门面，供 HTTP 和本地作业调用；每个功能使用独立的命令 DTO、状态规则与数据表。`Record` 是持久化信封，消费者接口只接受有限的业务命令，不开放任意 JSON 表写入。权限检查与裁剪在业务层，不能依赖客户端隐藏按钮。

## 数据选择与一致性

迁移 007 为每种聚合建独立 `mobile_*` 表，复用原 `users` 身份，原业务表保留。所有权、参与方、关联 ID、媒体引用、唯一业务键、版本与时间为关系字段；复杂版本/披露内容使用带明确 Go 类型的 JSONB。表间 FK 保护确定的父子关系；跨类型引用由命令在同一事务中校验。

采用 JSONB 的目的是保存完整版本和结构化披露，不把全部业务塞进一张通用表。当前搜索在受限候选批次中执行；高流量后应按实际查询增加类型化列、复合索引与专用查询端口。现阶段没有声称已具备大规模吞吐。

写事务使用 PostgreSQL SERIALIZABLE，更新带版本条件。并发冲突返回 409，客户端重新读取后确认意图；不在服务端无条件重放可能已过期的用户确认。内存实现复制事务快照并提交，适合开发，不能作为生产持久化替代品。

通知记录和领域 Outbox 与业务变更一起提交。事件带模式版本、聚合类型/ID/版本、操作者；消费者以事件 ID 去重。`ops/outbox` 仅公开事件信封，排除验证码、会话和供应商凭据。外部消费者成功处理后才 ACK，未处理事件保留；未配置的系统推送不会被记录成已送达。

SMS、OAuth、Apple 撤销等网络调用在数据库事务之外。验证码先保留发送名额再标记供应商接受/失败；失败不留下可用验证码。Apple 撤销使用加密令牌和可重试作业，失败保持待处理。账号注销先停止登录、匿名化资料并撤下新业务公开内容，进入待清理状态，不能冒充全部历史数据已物理删除。

## 后续拆分路径

1. 根据实际负载或团队责任选择边界；优先独立媒体/推送作业，再考虑寻宠、消息或领养模块。
2. 保留现有 HTTP DTO；门面的方法由进程内调用换成明确的客户端端口，不能让服务共享任意 SQL 写权限。
3. 迁移该模块的数据所有权与独立 schema/数据库；其他模块只能通过 API 或事件访问。
4. Outbox 发布适配器接消息系统，增加消费者 Inbox 去重、重试、死信、可观测性与版本兼容。
5. 今天跨模块的事务（例如领养交接与宠物归属、群成员与邀请、账号与第三方绑定）届时需改成明确的编排/补偿或事件一致性，并增加故障场景验证。

这保留可拆分的接缝，不承诺零成本或一键切成微服务。服务拆分前必须依据真实流量、故障隔离或组织需求作决定。

## 与既有系统的迁移边界

新功能走 `/api/v2`，私有结果不进入旧 Redis 共享缓存。生产默认关闭 v1 写接口，避免旧私信/订单/领养接口绕过新规则；旧公开读取仅用于历史兼容，不把 v1 数据当成新隐私模型的证明。开发兼容必须显式打开。

可选 `migrations/backfill/legacy_to_mobile.sql` 保留来源数据，以私有草稿和待核对历史申请导入。不会将关注边自动转为好友、将旧状态转为双方交接、将支付桩结果当成真实收款，也不会把未经新媒体流程处理的图片公开挂接。正式切换需备份、核对实际历史量和逐项确认映射；本轮没有执行导入。

现行[安全合同SC-AP](../design/MND_SAFETY_AND_LIFECYCLE_SPEC.md)统一旧冲突：普通协商保留effectiveVersion，pendingProposal单列；恢复旧内容新建版本并双确认。地点不可用、主体／宠物不符、健康重大纠正等具体风险另走safety_hold，停止按原安排出发，核对并双确认后解除。现有源码仅覆盖前半段，safety_hold等新增合同尚未实现，不能因设计更新宣称后端完成。

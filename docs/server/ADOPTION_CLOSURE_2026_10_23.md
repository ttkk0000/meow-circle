## 3. 服务端源码

| 改动 | 具体行为 |
|---|---|
| `internal/mobile/adoption_placement.go` | pet行作为共同事务检查对象，扫描其他活动试养／交接／接回；取得安排前重核双方成年资格；其他已通过候选转候补并发中性通知；交接完成关闭其他非终态申请 |
| `rescue.go` | 试养双方确认／直接交接取得唯一占用；记录版本及幂等保持；申请请求绑定adoption_cycle，新周期不同键；新增resubmit／resume_candidate，候补可退出 |
| `social.go`、`models.go` | 服务端维护周期和公开安排状态，客户端不能指定；关闭后重新开放递增周期，结束旧活跃申请；已有安排时不允许重新开放或直接删除pet |
| `contracts.go` | 接回提交计发起方确认；本人withdraw、对方decline；accept实时拒绝过期；生效／实际接回完成重核双方成年资格；保留原有效安排；实际接回后清占用但不自动重新开放；双方收到进度通知 |
| `offers.go`、`appointments.go` | 已有活动领养安排不能靠保存新报价或从报价创建／变更预约绕过；保持同一pet检查 |

字段使用既有JSON数据列，本批没有新表／新DDL或依赖；旧数据缺周期按0兼容，旧客户端省略周期只适用于周期0。已有008迁移仍未执行。本批没有真实数据回填；历史多活动安排需要先按runbook核对，不能自动选赢家。

当前实现会扫描同宠的关联申请；记录分页不等于关联总量或事务耗时有界。PostgreSQL行锁／Serializable、并发冲突、失败回滚和实际数据量需要运行验收。source级检查不能证明数据库执行行为。

## 4. 公共KMP与Android

Models及AdoptionInput接入周期与安排状态，MobileApi提交当前宠物周期；本机原请求／原载荷恢复沿用既有协议。MobileStore显示候补／其他安排结束／接回阶段，提供本人重提及退出候补，不自动进入试养。Android接回页区分发起人撤回与接收人拒绝，展示截止、过期和当前有效安排；服务端时间与资格为最终关卡。没有修改iOS UI。

新API动作：`POST /api/v2/adoptions/{id}/resubmit`、`resume_candidate`、`returns/withdraw`。既有通用handler分派到业务方法；export_mobile_contract同步OpenAPI，新增3路径。公共请求字段检查同步adoption_cycle；未用新客户端请求兜底旧服务。

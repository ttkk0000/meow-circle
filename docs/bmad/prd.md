## 1. 执行摘要

M&D 以交流和领养为主，补充售猫与有偿转让的信息和预约能力。用户要解决的具体问题是：找到渠道后，无法确认谁在发布、猫在哪里、谁会接待、是否有代理，以及到场后猫、地点和费用会不会变化。

个人、商家、猫舍和公开关系的代理均可参与。家庭饲养不作为可信前提。平台以主体核对、关系披露、分项证据、预约快照、变更确认和到访反馈建立可追溯记录。

**本版规划假设：** 先做信息与预约，不代收款、不提供支付担保或赔付。用户尚未决定完整交易服务；本文件不把这项假设描述为已批准商业模式。

现行主导航按已批准Figma为“社区 / 领养 / 发布 / 消息 / 我的”，互助与出售分支从相关上下文进入；出售明确标注“出售与有偿转让”。新移动端采用Figma V2默认浅色；旧Stitch镜像与未迁移旧端按各自规则保留，不重新等待旧视觉映射批准。

### 2.3 业务目标

- G1：用户出发前能确认发布方、猫、接待方、地点和费用。
- G2：发生关键变化时，用户可知情接受或退出，并保留原信息。
- G3：救助方可管理申请、交接和回访，社区保留持续关系。
- G4：平台能基于证据处理不符、冒用、骚扰与申诉。
- G5：通过单城试点验证反馈覆盖率、信息一致性和运营成本。

## 3. 用户与角色

账号可以拥有多项权限。账号主体、对单只宠物的关系、核验状态分别建模。

| 用户 | 主要任务 | 权限边界 |
|---|---|---|
| 访客 | 浏览社区、领养、售猫信息与公开摘要 | 不访问私密申请、精确个人地址或证件 |
| 注册用户/意向买家 | 咨询、收藏、预约、反馈、举报 | 无需填写整套领养家庭调查 |
| 领养申请人 | 申请、补充、撤回、交接与回访 | 仅查看本人资料及获授权信息 |
| 个人转让者 | 发布有偿转让或送养信息 | 按每条信息披露性质和关系，不能以个人身份规避必要核验 |
| 商家/猫舍 | 发布、授权员工接待、管理报价与预约 | 公开经营主体及必要信息；销售声明需证据支持 |
| 代理/员工 | 获授权发布、接待或代售 | 明示代理对象、职责、费用和授权范围 |
| 救助者/机构 | 发布领养、管理申请与回访 | 领养通道不承载隐性商业收费 |
| 审核员/管理员 | 处理核验、投诉、申诉与授权 | 独立后台；最小权限；访问与动作留痕 |

## 4. MVP 范围

优先级标记：MUST=必须；SHOULD=应该；COULD=可选；WON'T=本轮不做。低优先能力不能挤占最低可用闭环。

| 阶段 | 能力 |
|---|---|
| R0 案例与规则验证 | 约 10 个案例回放；访谈买家、救助者、个人、商家和代理；确认字段、变更与投诉路径 |
| R1 必须闭环 | 基础社区；领养浏览/申请/交接；找猫信息；主体/授权与关系披露；价格必付项；近期材料；预约快照；变更再确认；反馈；举报复核；隐私与事件 |
| R1 可人工承接 | 主体核验、部分材料复核、回访提醒、争议调查；必须有受控记录与负责人 |
| R2 增强 | 收藏、资料工作台效率、回访自动化、安家故事、机构协作、医院材料验证、小程序 |
| 后续独立决定 | 完整支付、担保、售后赔付、跨城运输、泛用品商城与公开募捐 |

社区与领养保持核心入口和内容投入。找猫作为补充服务，不以售猫付费曝光挤占领养推荐。

## 5. 领域与状态

### 5.1 领域边界

- 宠物档案描述猫/犬；发布信息说明领养或出售性质、关系与条款。两者不混为商品订单。
- 账号核验不能自动覆盖所有档案和场所；证据结论绑定事项、对象和版本。
- 商业主体、照护方、接待方和预计收款方允许不同，需核对关系与授权。
- 同一猫的重复信息应关联同一档案并复核，不靠换账号绕过状态；无证据不得自动合并两只相似猫。
- 领养申请与看猫预约是不同流程，共享会话与信任材料，不共用不适当的申请表。

### 5.2 状态转换表

| 对象 | 正常转换 | 关键限制 |
|---|---|---|
| 审核 | draft → pending → approved；pending → needs_changes/rejected；approved → suspended/archived | 审核通过不等于所有事项核验通过 |
| 公开可用性 | available ↔ paused；available → reserved；reserved → available/rehomed；任意非终态 → withdrawn | rehomed 区分领养/出售结果；不等于已付款 |
| 核验证据 | missing → pending → valid；pending → needs_changes/rejected；valid → expired/revoked/disputed | 未知与失败分开；到期或关键变更后不能沿用标签 |
| 领养申请 | draft → submitted → reviewing；reviewing ↔ needs_info；reviewing → accepted → closed | 活跃申请可 withdrawn/rejected/expired；accepted 不代表已交接 |
| 预约 | proposed → confirmed/declined/cancelled/expired；confirmed → completed/cancelled/change_pending；change_pending → confirmed/cancelled/expired | 关键变更只能新建版本；不以超时默认接受 |
| 领养交接 | matching → trial（可选）→ handover_pending → confirmed；试养失败返回匹配 | 双方确认或人工有据介入；宠物状态与申请结果需一致 |
| 回访 | scheduled → submitted → completed；scheduled → overdue；submitted → risk_review | 与宠物可用性分开，避免“回访中”被理解为可领养 |
| 投诉 | received → reviewing → upheld/not_upheld/inconclusive → closed；可 appeal → reconsidered | 无反馈、证据不足不等于没有问题 |

暂停后恢复须记录原因并重新满足发布/核验门槛。已完成交接后的退养或重新转让创建新的处理与发布版本，关联原交接记录；不得静默把原成功记录改回可用，以免丢失真实历史。

预约由双方确认同一版本后才为 confirmed。completed 表示预约过程已记录结束，不等于已成交；未到访、失联或双方对到访有争议应分别记录结果，不能自动生成一致反馈。

普通协商变更将effectiveVersion与pendingProposal分开，原有效安排保留；拒绝／撤回／到期只结束提案，不自动接受新安排。恢复旧内容也形成新提案版本，不能复活旧确认。原地点不可用、宠物／主体失实、重大健康或费用纠正等安全事件另走safety_hold，明确停止按原安排出发；解除需核对并双确认新版本。取消、未到访、失联和到访争议分别记录。完整替代规则见安全合同SC-AP。

## 6. 功能需求

### 6.1 统一入口与社区（EPIC-001）

#### FR-001：统一导航【MUST】

提供社区、领养、发布、消息、我的五个主入口；取消强制三模式选择，同城互助（走失/拾获）与可信找宠（出售/有偿转让）从相应上下文进入，页面内与个人工作台发布入口复用同一发布向导。

**验收标准：**
- 新用户可直接浏览，不为查看公开信息强制注册。
- 旧模式偏好迁移后保留账号、内容、历史申请与必要订单查询，不丢失原数据。
- 本轮不把旧订单入口当首屏任务；未迁移历史订单不能直接删除。

#### FR-002：角色工作台【MUST】

同一账号根据权限显示救助、商家或代理任务。

**验收标准：**
- 申请人、发布方和审核员只能访问各自授权资源。
- 商家可以发布真实救助信息；每条信息性质独立明确。
- 消费者不能通过隐藏地址或直接 API 访问后台数据。

#### FR-003：账号与发布权限【MUST】

互动、申请、预约、发布需登录；宠物信息公开发布前完成适用的主体与授权核验。

**验收标准：**
- 登录后返回原任务；草稿保留。
- 员工/代理只能操作获授权档案；撤权后立即失去新操作权限。
- 不把普通注册手机号描述为完整身份或经营资质核验。

#### FR-004：社区浏览【MUST】

支持日常、互助、救助日记和安家故事；商业内容明确标注性质。

**验收标准：**
- 帖子可关联已授权宠物档案，跳转显示最新状态。
- 救助与广告不能以同一“免费领养”外观混淆。
- 空态、加载失败与演示数据具有可辨识说明。

#### FR-005：发布与草稿【MUST】

提供动态、领养和出售三类任务模板，并按身份与材料门槛开放。

**验收标准：**
- 草稿可恢复；提交失败不清空；重复提交不重复建档。
- 出售与有偿转让进入商业披露模板，不能借普通帖子绕过准入。
- 关键公开字段变更进入相应复核与通知流程。

#### FR-006：内容关联与收藏【SHOULD】

内容和收藏引用稳定档案，不复制过期“可申请/可预约”状态。

**验收标准：**
- 暂停、已安家或撤回后旧内容同步提示。
- 用户不能将帖子绑定到无权操作的猫档案。

### 6.2 主体、宠物与核验（EPIC-002）

#### FR-007：分项核验【MUST】

按主体、授权、场所、近期猫咪材料、医疗材料分别展示结论。

**验收标准：**
- 每项显示核验范围、方法类别、时间、有效状态和局限。
- “材料已上传”和“来源已确认”明显区分。
- 过期、撤销和有争议的结论不继续显示为有效。

#### FR-008：结构化宠物档案【MUST】

记录物种、外貌、年龄及其确定性、性别、当前区域、照护、疫苗/绝育、已知健康与特殊照护。

**验收标准：**
- 未知项可明确标为未知，不强迫救助猫编造父母/繁育信息。
- 出售的具体猫具备可辨识媒体与稳定标识，不能只发品种库存图。
- 公开摘要与私密原件分离。

#### FR-009：审核与版本【MUST】

新发布、关键关系/健康/价格声明变更支持审核和版本留存。

**验收标准：**
- 审核支持补充、通过、拒绝、暂停与理由。
- 关键变更提示已有意向用户；预约快照不被新版覆盖。
- 无法证明的声明不得显示为平台已验证。

#### FR-010：可用性与交接状态【MUST】

宠物可用性、审核、申请、预约和交接各自有状态，并按业务规则协调。

**验收标准：**
- 已撤回或暂停不能接受新申请/预约；旧记录仍可查询和投诉。
- 单方自报售出不生成平台已验证成交。
- 状态非法跳转由服务端拒绝，客户端提供可恢复提示。

### 6.3 领养（EPIC-003）

#### FR-011：领养发现【MUST】

按城市、物种、年龄和照护条件浏览领养。

**验收标准：**
- 未授权定位时可手动选城；不要求精确定位。
- 售猫不能混入“无偿领养”筛选；合理支出在详情前可见。

#### FR-012：宠物详情【MUST】

详情展示信息性质、档案、主体关系、核验摘要、费用/要求和下一步。

**验收标准：**
- 领养为申请与联系；出售为查看披露、咨询与预约。
- 主体不同或有代理在主内容区可见，不折叠隐藏。
- 未核验/未知字段不使用确定性肯定文案。

#### FR-013：领养申请【MUST】

按必要目的收集城市、住房/安全条件、现有宠物、经验、照护和回访意愿。

**验收标准：**
- 草稿、预览、同意、提交与编号齐全；同猫同申请人只能有一个活跃申请。
- 不在初始表单强制身份证照、完整住址和私人金融资料。
- 买猫预约不使用此表单。

#### FR-014：补充、撤回与结束申请【MUST】

支持标准问题补充、撤回、拒绝和合理过期。

**验收标准：**
- 补充要求说明必要性，禁止任意索取过量资料。
- 结束后隐藏非必要家庭资料，但依法需保留的争议记录受控保存。
- 不以未回应默认同意申请条件。

#### FR-015：救助方申请工作台【SHOULD】

提供按猫和状态查看、补充与推进申请。

**验收标准：**
- 默认摘要展示，不能批量下载完整敏感资料。
- R1 可人工处理部分任务，但身份权限、状态和日志不能省略。

#### FR-016：领养约见与试养【MUST】

双方可确认地点、接待方及约见，试养为可选步骤。

**验收标准：**
- 复用预约版本与变更规则。
- 在医院等第三地点见猫允许，但关系和安排先披露。
- 试养前明确期限、照护、退出和异常联系人。

#### FR-017：交接与异常承接【MUST】

领养双方确认交接，试养失败或退养可求助原救助方和平台。

**验收标准：**
- 只有双方确认或有审计的人工结论才标记已交接。
- 退出不公开申请人敏感原因，也不自动转成售猫信息。
- 售猫交接与售后责任使用商业条款，不能套用救助方兜底义务。

### 6.4 沟通与回访（EPIC-004）

#### FR-018：上下文会话【MUST】

会话可关联宠物、申请或预约，显示当前版本与下一步。

**验收标准：**
- 同一双方讨论不同猫时上下文不串联。
- 聊天里“好的”不自动替代关键变更的明确确认。
- 发送失败可重试并防重复，草稿不丢失。

#### FR-019：关键通知【MUST】

申请、预约、变更、核验失效、投诉和回访有站内通知。

**验收标准：**
- 通知到对应上下文；正文不含私人地址/证件。
- 业务成功但推送失败不回滚业务，可重试；用户在站内可见。

#### FR-020：领养回访与到家反馈【MUST】

R1 保留可人工提醒的 30 天领养回访与风险求助；买猫提供独立可选到家反馈。

**验收标准：**
- 回访默认私密；领养未完成交接不能进入成功指标。
- 买猫未回访不被记作违约，也不获得无病保证。
- 7/90 天自动任务为 R2 SHOULD，不作为 R1 的强制开发范围。

#### FR-021：安家故事【SHOULD】

用户可把脱敏回访转成公开内容。

**验收标准：**
- 默认不发布，先预览并主动选择。
- 删除故事不静默删除必要业务证据。

### 6.5 安全与数据（EPIC-005）

#### FR-022：举报、屏蔽与受理【MUST】

支持身份、猫、地点、费用、代理、健康声明不符及骚扰等分类。

**验收标准：**
- 无预约码也可举报，不能因缺少平台记录拒绝受理。
- 单方报告为待核实；不自动公开“骗子”标签。
- 紧急风险有优先级和受理状态，举报人身份不公开。

#### FR-023：复核、暂停与申诉【MUST】

授权后台比较声明、材料、预约版本与双方证据。

**验收标准：**
- 暂停新增预约、下架、撤销核验等动作需理由和审计。
- 被处理方有补充和申诉入口；改判可追溯。
- 高频、多品种、多地址作为信号，不能直接自动认定欺骗。

#### FR-024：隐私与访问控制【MUST】

公开信息、预约地址、申请家庭资料、主体证件和原始视频分权限处理。

**验收标准：**
- 敏感字段不进入公共响应、分享卡或分析日志。
- 私人地址只在必要的预约确认流程中授权双方；经营公示另按适用要求配置。
- 撤回/注销支持非必要资料删除与必要证据受控保留。

#### FR-025：透明售猫与反欺骗【MUST】

允许真实商业售猫，禁止借领养隐藏交易性质或捆绑义务。

**验收标准：**
- 经营主体、代理关系、收费和责任方真实披露后，不能仅因其为商家或代理而拒绝。
- 冒用主体、隐藏强制费用、盗图调包或未确认转场进入复核。
- 不以“家庭”“无中介”作为总括认证标签。

#### FR-026：分享与深链【SHOULD】

提供可无需安装查看的脱敏公开页。

**验收标准：**
- 分享页反映最新状态；缓存不得持续提供失效申请/预约入口。
- 登录后回到原上下文；不得分享精确私人地址与原始材料。

#### FR-027：事件与指标【MUST】

统计两条业务结果和分项信息不符。

**验收标准：**
- 区分买家反馈、卖家自报、双方确认和平台审核结论。
- 反馈缺失不计入一致；样本量与覆盖率同时展示。
- 事件不采集聊天正文、家庭资料和金融账号。

### 6.6 可信找猫（EPIC-006）

#### FR-028：每猫关系披露【MUST】

披露发布主体、照护方、来源说明、代理、接待方、预计收款和责任方。

**验收标准：**
- 允许各方不同，但要说明授权与分工。
- 无足够发布授权或故意隐瞒关键关系时不能新增预约。
- 完整字段与权限遵循[真实性规范](../design/MND_TRUST_AND_DISCLOSURE_SPEC.md)。

#### FR-029：近期材料与替代核验【MUST】

每条公开售猫信息具备近期猫咪与环境材料，平台可按风险要求随机任务复核。

**验收标准：**
- 材料与单只猫、任务和时间关联；支持人工视频等替代方式。
- 过期和关键变化触发复核；复核期间状态明确。
- 结论只描述所核对事项，不推导所有权、亲生、无中介或健康保证。

#### FR-030：完整价格与必要费用【MUST】

预约前提供具体报价、必付项、总额和可选项，标明预计收款与代理费。

**验收标准：**
- 不用低价库存图或隐藏捆绑项目引流。
- 因用户选项产生的报价有明确版本，未知总额不能当作已确认价格。
- 未接入支付时“预计收款方”为声明，不标为实际付款核验。

#### FR-031：预约确认快照【MUST】

双方确认同一版本的猫、接待方、地点、时间、价格、必付项和责任条款。

**验收标准：**
- 快照不可被后续编辑覆盖，双方可查看自己的确认版本。
- 拒绝或超时不会自动成为已确认预约。
- 私密地址与公开页面分权限，快照不暴露给无关用户。

#### FR-032：关键变更重新确认【MUST】

猫、地点、接待方、价格/必付项、预计收款方、代理关系、已知健康情况或交接/售后责任条款变化后生成新版本。

**验收标准：**
- 页面展示差异并进入 change_pending，新安排未确认前不能显示为“已确认”。
- 用户可接受、拒绝或取消，拒绝后不计为无故失约。
- 现场主动换猫建立新关联记录；原猫的到访结果保留。

#### FR-033：到访分项反馈【MUST】

买家分别反馈猫、接待身份、地点、价格与必付项的一致、不一致或不确定。

**验收标准：**
- 无成交也能反馈；卖家不能代填买家结果。
- 到访码只关联预约，不单独证明实地到场。
- 缺失反馈与不确定不进入“一致”分子。

#### FR-034：有依据的评价与处理结果【SHOULD】

公开评价显示预约/反馈/交接依据类型，处理结果区分待核实与结论。

**验收标准：**
- 卖家不能删除有效差评，平台可按规则脱敏和复核。
- 没有成交不妨碍报告虚假带看；评价准入不能成为投诉门槛。
- 不公开证件、私人地址、未核实人身指控。

### 6.7 扩展业务模块与全量设计闭环（EPIC-008，2026-10-24 整合补充）

以下需求将已落入专项规范、Figma 五端 740 状态与 `F00`–`F14` 源码矩阵的扩展能力正式纳入主 PRD 编号体系，与 `FR-001`–`FR-034` 共同构成完整业务合同。

#### FR-035：三唯一标识认证、交流前手机号验证与年龄监护分层【MUST】

账号区分不可变内部 `user_id`（主键，不对外公开）、公开可变展示 `display_handle`（`@handle`）与公开只读数字 `public_uid`（搜索/核对）；支持用户名/邮箱密码、邮箱验证码（OTP）注册登录，以及微信、QQ、iPhone Sign in with Apple 快捷登录。任何交流或写操作（发帖、评论、私信、群聊、加好友、入群、领养申请、看宠预约、走失线索提交）前必须完成服务端校验的手机号绑定与年龄分层校验。

**验收标准：**
- 取消未注册手机号短信自动建号，验证码与重置密码接口采取枚举保护与频率限制。
- 年满 14 周岁并完成手机号验证可正常交流与发布日常内容；未满 14 周岁须绑定已核验监护人授权后方可互动，且默认关闭陌生人私信、公开群、精确位置与商业交易入口；商业发布、有偿转让与线下领养/购宠签约须年满 18 周岁。
- 协议勾选遵循《个人信息保护法》最小必要原则：必选《用户服务协议》《隐私政策》及按年龄段呈现的《儿童个人信息保护规则及监护人须知》，个性化通知与营销授权独立可选且默认不勾选。详见[认证规划](../design/MND_MOBILE_AUTH_PLAN.md)与[安全生命周期合同](../design/MND_SAFETY_AND_LIFECYCLE_SPEC.md)。

#### FR-036：单向内容关注、求助订阅与双向好友宠友圈【MUST】

区分单向公开关注（用户与宠物档案）、公开求助动态订阅（走失/拾获进展通知）与双向确认好友关系；提供仅双向好友可见的“宠友圈”私密动态流与独立可见性控制。

**验收标准：**
- 单向关注或订阅公开求助不需要对方审批，也不解锁非好友私信免限额或宠友圈可见权。
- 双向好友必须经过“发起申请 → 对方确认”或双方互认，支持备注、分组、宠友圈权限设置、解除好友与拉黑屏蔽；拉黑后立即阻断私信、好友申请与互动提醒。
- 动态发布支持选择“公开社区”或“仅双向好友（宠友圈）”，公开列表与分享外链不得泄露宠友圈动态。

#### FR-037：多宠物档案、其他允许物种与介绍/照护双类协作【MUST】

支持同一用户名下创建和管理多只宠物档案（猫咪优先，兼容狗狗及兔兔、仓鼠、豚鼠等合法伴侣小宠，严禁受保护野生动物与城市禁养烈性犬），每只宠物具备独立日记时间线、相册、疫苗/体检记录与关联帖子；支持按单只宠物邀请协作者并严格区分“介绍协作者”与“照护协作者”。

**验收标准：**
- 切换当前宠物档案时，日记、成长记录、相册与关联动态按单宠隔离，不混用其他宠物的医疗或核验状态。
- “介绍协作者”（如摄影、文案、助宣志愿者）仅可编辑公开介绍与媒体建议，无权修改健康声明、核验材料或确认申请/预约；“照护协作者”（如共同饲养人、寄养家庭、授权门店照护员）可更新日常照护记录与协助接待，但主体变更、送养/出售交接最终确认仍受主档案所有人与平台授权规则约束。
- 协作者可随时接受、拒绝邀请或主动退出，主所有人可随时撤权并留存操作审计日志。

#### FR-038：公开群发现、入群申请审核与群主角色移交【SHOULD】

支持按同城区域、养宠主题与互助圈发现公开群组，提供群资料预览、入群申请与管理员审核、群成员管理、群内举报以及群主主动移交群管理权后再退群的完整闭环。

**验收标准：**
- 群组列表标注群性质（日常交流/同城互助/救助协作），禁止以公开群名义开展未核验活体拍卖或违规引流。
- 需要审批的群组提交入群说明后进入 `pending`，审核通过后方可发言；未满 14 周岁账号按年龄分层规则限制加入公开陌生群。
- 群主退群前若群内仍有成员，必须先指定并完成新群主移交或解散群组，防止产生无主失管群。

#### FR-039：同城走失与拾获互助、私密目击线索与粗精度地图（武汉/上海冷启动）【MUST】

以武汉、上海为冷启动试点；大陆城市目录兼容不等于业务开放，按城市／物种／行为准入规则提供独立的“走失求助”与“拾获招领/临时安置”发布、筛选、粗精度网格/街区地图浏览与私密目击线索提交通道。

**验收标准：**
- 公开页面与地图打点仅展示街区/商圈级粗精度范围与必要特征摘要，严禁直接公开报案人私人门牌、家庭住址或引发围捕骚扰的实时精确定位。
- 目击线索默认仅向求助发布者及平台安全审核人员私密投递，支持附带时间、粗略位置与照片，不直接作为已核实事实公开广播。
- 拾获认领交接前须核对原饲养特征凭证（历史照片、芯片/免疫本或独特印记），防止冒领；状态变更为“已团聚/已撤回”后地图与分享页同步停止求助征集。详见[冷启动与走失互助规范](../design/MND_COLD_START_LOST_PETS_AND_AUTH_SPEC.md)。

#### FR-040：表情序列与 24 张固定贴纸（144 方形保比例）富内容输入【SHOULD】

在社区发帖、评论、宠友圈、私信与群聊输入栏提供底部表情面板，支持基础行内表情序列（如 `[微笑]`）与 24 张猫咪/狗狗主题固定大贴纸（`[贴纸:名称]`），并保持跨端一致渲染。

**验收标准：**
- 表情面板遵循底部键盘切换状态机，切换时不丢失已输入的正文、关联宠物或图片草稿。
- 24 张固定贴纸在消息流与详情中采用 144×144 方形容器等比缩放（`FIT`/居中保比例），不得拉伸变形。详见[微信式底部表情交互](../design/figma-study/WECHAT_STYLE_EXPRESSION_INTERACTION.md)与[贴纸比例核查](../design/figma-study/EXPRESSION_ASPECT_2026_10_23.md)。

#### FR-041：全局未读（`99+`）、三分类消息中心与十分钟确认快照全部已读【MUST】

底部导航与顶部消息入口汇总全局可消除未读数（超过 99 显示 `99+`），消息中心固定划分为“私信与群聊 / 互动提醒 / 系统与业务通知”三分类，并提供带 10 分钟服务端确认快照的“全部标为已读”能力。

**验收标准：**
- 全局未读数等于三分类未读之和；免打扰会话计入分类列表弱提示但不虚增底部强红点；需用户明确处理的业务动作（如待确认预约变更、待响应试养接回）即使已读通知也不等同于业务已同意。
- 点击“全部已读”须经过二次确认，执行前创建服务端快照，10 分钟内按快照编号／版本确认；只核销快照内仍可处理的未读，操作后新增消息保持未读。快照超时须重新获取；当前合同不提供成功后撤销已读。详见[全局未读规范](../design/MND_GLOBAL_UNREAD_SPEC.md)。

#### FR-042：用户资料级举报、免注册安全求助、正式权利通知与照护指南/规则历史独立阅读页【MUST】

除帖子、宠物档案、会话与预约外，支持对用户个人主页（冒充身份、违规头像/昵称/简介、私信骚扰）直接发起举报；提供无需登录即可提交的违法/虐待/隐私泄露紧急报告与正式权利人侵权通知通道；并在端内提供完整的照护指南详情、平台规则详情及规则历史版本对照独立阅读页。

**验收标准：**
- 个人资料页举报自动固化被举报方当时的 `public_uid`、`display_handle`、头像与简介快照；免注册游客安全报告与权利通知独立生成回执编号。
- 领养/找宠/互助中的照护指南卡片、平台协议与公示规则均跳转端内独立阅读页（`guideDetail` / `ruleDetail` / `ruleHistory`），包含适用物种、关键核对清单、生效日期、历史版本摘要与变更对比，不以空白外链或死按钮替代。详见[合规补充规范](../design/MND_LEGAL_DESIGN_SUPPLEMENT_2026_10_22.md)与[双城准入及标准协议草案](../design/MND_CITY_SPECIES_AND_CONTRACT_TEMPLATES.md)。

## 7. 非功能需求

以下为设计目标，尚未经过容量测量或发布验证。

#### NFR-001：响应性能【SHOULD】

正常试点负载下，列表/详情 API P95 目标 ≤800ms；统计不含客户端媒体下载，实际负载由架构阶段定义。失败可重试，表单不因刷新丢失。

#### NFR-002：数据一致性【MUST】

提交、预约确认、关键变更、交接和消息重试具备幂等与并发版本检查。旧版本确认必须拒绝或要求刷新，不能覆盖新条款。

#### NFR-003：身份与权限【MUST】

服务端校验角色、资源归属、授权范围及状态；原件访问和后台动作留痕。仅隐藏按钮不能通过验收。

#### NFR-004：隐私与保留【MUST】

传输加密；敏感材料隔离、限制访问、分析脱敏。上线前逐类定义保留目的、期限、撤回/注销与争议例外，不把“不收款”当作责任豁免。

#### NFR-005：恢复与审计【MUST】

快照、核验、变更、处理和申诉可恢复、可追溯。上线前确认备份与恢复方案；不能仅保留最新编辑结果。

#### NFR-006：可访问性【MUST】

Web 目标 WCAG 2.2 AA；关键文字对比度 ≥4.5:1，非文字控件 ≥3:1；键盘、TalkBack/VoiceOver 语义、字体放大和 reduced-motion 纳入后续验收。原生关键触控区采用 48dp/44pt 平台目标；不可只用颜色区分核验状态。

#### NFR-007：多端与视觉【MUST】

业务状态、字段含义、核验标签和错误码跨端一致；新移动端使用已批准Figma V2默认浅色、字体及组件和五主入口。旧Stitch四主题仅保留未迁移旧端参考，不新增主题选择器。手机／平板独立适配，当前先Android、苹果UI后置；完整各端标准保留。现行闭环补充见[2026-10-23合同](../design/MND_PRODUCT_CLOSURE_CONTRACT_2026_10_23.md)。

#### NFR-008：运营可执行性【MUST】

公开内测前有负责核验、风险与申诉的人员、值守时段和可量化受理时限。目标普通投诉 24 小时内首次响应；未具备排班时不能对外承诺全天即时处理。

## 9. 用户体验要求

具体屏幕与失败路径以 [UX 规格](ux-design.md) 为准，证据与字段以[真实性规范](../design/MND_TRUST_AND_DISCLOSURE_SPEC.md)为准。

- UI-001：社区保持生活与交流入口；领养和出售卡片性质持续可见。
- UI-002：详情主内容区显示主体关系、核验范围、地点类型和费用，重要信息不能藏在免责声明或折叠末尾。
- UI-003：预约确认显示可读摘要；变更逐项显示旧值、新值和明确动作。
- UI-004：拍摄/核验提供替代方式；不强制公开家庭环境与成员。
- UI-005：表单错误关联字段；加载、提交、成功、失败、空态、失效和争议状态可访问。
- UI-006：演示和实时内容可辨，演示交接或核验不能显示为真实结果。

## 10. 成功指标

本轮没有真实业务基线，下列为定义与试点假设，不是增长预测或上线承诺。

| 指标 | 定义/分母 | 试点目标 |
|---|---|---|
| 领养结果 | 双方确认交接，30 天回访有效的猫数 | 建立基线，逐例复盘 |
| 找猫结果 | 有完整快照，买家有反馈且关键事项均一致的到访数 | 建立基线，不称“平台验证成交” |
| 到访反馈覆盖率 | 买家已反馈 / 到期未取消预约；单列未确认是否到访 | 初始目标 ≥60%，样本需一并展示 |
| 分项不符率 | 某项不符 / 该项有明确反馈的到访 | 持续观察，不先编造下降幅度 |
| 变更再确认率 | 已重新确认的新安排 / 需确认变更 | 平台动作应为 100%；线下绕行单列报告 |
| 公开信息完整率 | 必填披露完整 / 可预约信息 | 发布门槛 100%，不代表内容已全真 |
| 投诉首次响应 | 受理至首次实质响应 | 值守与容量确认后目标 ≤24h |
| 复核质量 | 申诉改判、无法判定与重复违规分别计数 | 建立基线，不追求低举报量 |

关键事件：`offer_published`、`verification_updated`、`application_submitted`、`appointment_proposed`、`snapshot_confirmed`、`change_requested`、`change_declined`、`visit_feedback_submitted`、`handover_confirmed`、`followup_submitted`、`report_received`、`appeal_resolved`。只记稳定 ID、版本、分类和必要时间，不记敏感正文。

## 11. 假设、依赖与发布门槛

| 依赖 | 要验证什么 | 未满足时 |
|---|---|---|
| 首城供给 | 至少覆盖救助、个人、商家及已披露代理的样例 | 邀请内测，不开放全城发布 |
| 运营资源 | 能完成材料核对、风险处置、申诉与记录 | 缩小人数，不用自动认证代替 |
| 主体及授权方法 | 材料够用且不过度收集 | 先走人工方案并保留结论范围 |
| 可用性走查 | 用户看懂关系、总价、差异和退出 | 修订模板与文案后再开发 |
| 平台服务责任 | 实际业务所需经营公示、数据保护、投诉义务 | 明确适用范围后上线，不以无支付豁免 |
| 客户端适配 | 统一导航与旧模式、订单资料兼容 | 分端迁移；不要一次推倒现有代码 |

R0 通过案例回放后才能评估人力与日期；取消旧版未经估算的“12 周完成全量 MVP”承诺。R1 采用邀请制：必须能回放完整证据链并有负责人处理不符。R2 是否扩城取决于反馈覆盖、处理成本和重复违规，而非只看到访总量。

## 12. 本轮不做与后续考虑

- WON'T：支付代收、订金担保、赔付承诺、金融分期、自动成交结算。
- WON'T：用“家养”或“无中介”总括认证；按举报量直接定性；按未回复自动确认。
- WON'T：把商品市集、跨城运输、直播、募捐并入首版。
- COULD：合作医院材料核对、机构协作、7/90 天回访自动化、小程序轻量入口。
- 售猫信息、明确价格和预约属于 R1；不能再被旧版“活体销售全禁”排除。
- 领养通道仍不得伪装售猫和捆绑收费；商业销售使用明确性质的找猫路径。

## 13. 风险与取舍

| 风险 | 应对与边界 |
|---|---|
| 商家与个人合谋拍材料 | 多证据与持续复核；视频只证明有限事项 |
| 员工、医院或合法代售被误伤 | 核对关系，不要求全部主体/地点相同 |
| 用户转微信后被换地点 | 提供回平台更新与截图受理；不承诺能控制现实行为 |
| 付费认证破坏公信力 | 付费不提高核验结论；准入与证据标准一致 |
| 反馈偏差、卖家刷评价 | 分依据与反馈覆盖，不把无投诉算安全 |
| 私人地址和证件泄露 | 按需权限、公开摘要脱敏、访问审计 |
| 健康问题或交接后疾病 | 区分自述与医疗证据；展示约定责任，不承诺医学保证 |
| 多端状态漂移 | 服务端权威、共享合同、版本校验与迁移 |

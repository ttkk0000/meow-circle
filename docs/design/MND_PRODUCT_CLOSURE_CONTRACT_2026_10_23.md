## 2. 领养：宠物、申请周期和活动安排

### 2.1 数据与不变量

- 宠物档案pet_id稳定；每次重新开放领养有递增的adoption_cycle。旧数据视为周期0，首次新建可从0兼容；关闭后重新开放才递增，修改介绍／暂时隐藏不制造新周期。
- 每个pet在任意时刻最多一个活动领养安排，覆盖独占试养、实际交接待确认、接回处理中。申请被批准或提出试养均不取得独占；试养双方确认、或直接交接首次确认时在服务端取得占用。
- 唯一占用、申请／候补、宠物公开可用性、通知在同一事务决定。记录级版本不能替代pet级一致性。另一申请已占用时拒绝旧确认，刷新当前状态，不泄露另一家庭、申请编号或材料。
- 同宠可有多份申请。其他已批准／试养提案转waitlisted；尚待审核的申请保留原状态，明确当前有安排，不能绕过占用进入试养／交接。新批准在占用期间也进入候补。
- 候补无排名承诺，不显示其他人资料。用户可以退出；下一位不会自动进入试养。安排结束且宠物重新满足准入后，送养方主动邀请继续，申请人再次确认条款。
- 交接完成后，其他非终态申请变为closed_other_placement并通知；原记录和投诉出口保留。相关出售信息关闭，公开可领养入口收起。不得把“已批准”当作已归属。
- 接回／试养退出不立即重新开放匹配。实际接回双确认后释放活动安排，宠物仍为不可领养；重新发布重新核对年龄、处分、城市、资料与来源，再开启新周期。
- 历史上如已有多段活动试养／交接，不自动选择赢家。标记需人工核对、停止新安排，保留当前照护与求助；迁移检查先输出最小冲突清单。

### 2.2 申请状态与再次申请

| 当前状态／触发 | 结果 | 页面动作 |
|---|---|---|
| 本周期首次申请 | submitted | 核对必要摘要并主动提交；保留原请求号 |
| 同一请求重试／重复申请 | 返回原记录，不重复创建 | 显示“查看本次申请” |
| submitted／supplemented被要求补充 | needs_info | 显示具体缺项、补充、撤回 |
| 送养方批准且无占用 | approved | 显示“候选已通过，尚未交接” |
| 已批准但另一安排取得占用 | waitlisted | 说明候补、查看历史、退出；不显示试养确认 |
| 本人撤回后本周期仍开放 | 主动resubmit，生成新事件／版本 | 重新核对摘要、资格和当前宠物；不自动重提 |
| rejected或closed_other_placement | 本周期终态 | 原记录只读、解释原因、申诉／返回；不靠换键绕过 |
| 宠物新周期开放 | 新申请，与旧周期记录关联 | 明示“新一轮申请”，不能恢复旧确认或照搬家庭原件 |
| 候补恢复 | 送养方主动resume_candidate后回approved | 双方仍须重新核对当前条款；不自动进入试养 |

申请请求绑定pet_id、adoption_cycle及当前摘要。旧客户端省略周期只兼容周期0；新周期不接受未知周期请求。展示周期无需向用户暴露内部编号，页面用“本轮领养／上轮记录”。每周期同一申请人一份记录；终态、重提和补充有事件历史。

### 2.3 领养画面与跨端

复用现有五布局原稿：candidates、trialReserved、waitlist、placementConflict、handoverWaiting、handoverComplete及接回系列。状态栏同时写“申请状态”和“宠物当前安排”；不用一枚“通过”标签表达全部状态。对方完成交接后，原页面刷新为只读终态，停止旧主按钮。

手机单列卡片＋底部主动作；平板可列申请摘要和当前选中详情，窄窗／键盘／大字时回单列。候补详情和失败提示最大阅读宽度沿现有适配合同；焦点不因列表更新跳到另一家庭。409回当前对象并保留输入；网络未知只核对原请求，不另建申请。

## 3. 安全接回：待确认提案、有效安排与实际接回分开

待确认提案的确认截止为该提案计划接回时间starts_at；页面显示具体当地时间及时区。到点仍未生效即不可接受，须重新协商；不因过期取消求助或释放宠物占用。后续如需更早截止，单独版本化配置，不在客户端猜测24小时。

| 动作 | 谁可以 | 前置／结果 |
|---|---|---|
| propose | 当前双方 | 新递增提案；发起人明确提交计本人确认；旧待确认提案变superseded；旧有效安排保留 |
| accept | 当前另一方或尚未确认的一方 | 同版本、未过期、资格及当前关系有效；两方确认后才生效；不表示实际接回 |
| decline | 非发起方 | 仅结束未生效提案；不是取消求助或否定全部接回责任 |
| withdraw | 发起方 | 只能撤回自己未生效提案；二次确认明确范围；旧有效安排／照护／求助不变 |
| expire | 服务端时间判断 | 过期提案拒绝确认并展示失效；后台维护可物化状态，但动作关卡不依赖定时器及时执行 |
| handover | 当前双方 | 只对当前有效安排分别确认；一方待确认，两方完成才returned；真实争议／误操作转协助 |

等待页显示发起方、双方确认、截止、照护及原有效安排；发起方看到“撤回本次提案”，接收方看到“拒绝本次提案”。撤回／拒绝／过期后的主动作是重新协商，次动作为查看求助进度，不显示“接回完成”。请求不明、失败、版本冲突、失权都有原用途恢复。

现有returnWithdraw／returnWithdrawn／returnExpired及R2变体继续作为画面依据；本次只补截止含义和当前有效安排说明，不重复铺设同一组画板。

## 4. 人员、可见范围和区域选择

人员选择只使用当前可访问的好友／群成员／明确打开的用户资料，按昵称筛选，显示头像、昵称和已有关系摘要；不默认提供全站手机号、邮箱或用户编号搜索。无结果、正在加载、失败重试、关系已解除分别展示。邀请前预览对方与本事项权限，成功后进入邀请列表，可撤回；不把内部ID作为普通输入项。

“指定好友／排除好友”用分页多选和已选摘要；关系变化后提交前重核。提交失败保留选择，已失权对象明确标记并要求调整，不能静默换成公开。隐私预览清楚区分“所有好友”和“仅以下好友”。

区域选择先选城市／区县，可选地图粗点；只需文字区域的求助不强制坐标。地图展示、获取当前位置和外部导航分别授权。SDK不可用或定位被拒绝时保留城市／文字列表；不把区中心伪装成精确事件点。公开／私密坐标与坐标系由合同区分，推送／分享只传公开粗摘要。正式地图／地理编码未接通时，用可读的城市区域输入及明确预览，不能要求用户查询经纬度。

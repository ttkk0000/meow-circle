# M&D 六处操作与状态合同

更新：2026-10-21。适用任务AI-20261021-LOGIC-FIX，依据[逻辑复审](figma-study/LOGIC_AND_DESIGN_REVIEW_2026_10_21.md)。本合同补充[安全生命周期合同](MND_SAFETY_AND_LIFECYCLE_SPEC.md)；不表示Go、OpenAPI或客户端已实现。

后续2026-10-22新增用途见[法律设计增补](MND_LEGAL_DESIGN_SUPPLEMENT_2026_10_22.md)及[交接／回读结果](figma-study/LEGAL_DESIGN_HANDOFF_2026_10_22.md)。其中事项协助与补充不替代LR06正式注销；侵权通知、被通知人声明及同案追加分别保留类型。新请求先清空上次结果，未知结果留在等待，勾选与当前用途／角色／版本均成立才可提交。

## 通用约束

- 每次受限操作携带当前账号、会话代次、原任务类型、对象ID、基准版本、草稿引用、当前角色和用途。回调只处理同一请求；账号切换、用途不符、过期或资源失权时拒绝恢复旧动作。
- 原任务恢复后重读资源、年龄／监护、当前手机号、角色及版本，仍需用户明确提交；验证不自动发帖、发消息或确认预约。
- 创建请求、查询结果、追加已有请求分别建模。写请求有幂等键；网络结果不明先查同次请求，不能拿另一条“成功示例”代替。
- 客户端自选年龄、原型运行变量和页面可达性不授予权限。真实资格、回执及成功只能来自服务端已确认结果。
- 待处理页的查询动作只读取结果：pending/unknown仍显示等待；confirmed结果才进入相应成功页，明确失败进入相应错误页。退出等待不自动撤销已发出请求。
- Figma评审中的结果示例放在画板外评审入口。应用界面不放“模拟通过／跳到已完成”按钮；可点击固定状态不当作生产验证证据。

## LR01 当前手机号的分用途验证

发送短信和核对验证码是不同请求。发送状态：pending→sent / rate_limited / unknown；验证码状态：pending→verified / invalid / expired / rate_limited / unknown。错误页始终保留当前号码和interaction_phone用途，不能进入邮箱登录或短信自动建号。

重新发送使用服务端返回的retryAfter和额度；等待期间不能新发。旧码过期后重新获取当前用途的新码，不更换账号绑定。原任务可为发帖、预约、私信、领养或寻宠；只恢复同账号原对象与草稿，未知目标回到安全站内入口。

## LR02 成年核对

资格页→用途与处理范围说明→已确认的核验服务→pending→passed / failed / not_eligible / expired / unsupported。取消或不可用保留原任务及受限状态，不跳账号列表冒充核对完成。

passed绑定账号、用途、来源与有效期，再回同一预约／商业任务检查手机、角色与资源。服务未配置时不可用分支优先，不假造核验方或收集公开证件。异议走独立人工复核，不由用户修改生日覆盖既有结果。

## LR03 安全暂停中的取消与报告

两条独立操作：
- 取消：显示预约对象与版本、原因、影响→明确确认→cancel_pending→cancelled / failed / stale。取消仅结束本次预约，原申请、会话、照护和必要证据按各自状态保留。
- 报告：关联同一预约的安全报告，不自动取消预约或把争议判为诈骗。

取消前返回或选择保留，仍回safety_hold。新提案、拒绝、撤回与超时都不解除hold；安全问题已核对且双方确认同一新版本后，才解除本次暂停。原取消稿若复用，“保留预约”不能跳到普通有效状态。

## LR04 接回提案的双边角色

1. A填写接回时间／时区、仅双方可见地点、接回人及授权、照护用品／用药、费用和责任；预览R1，明确提交。
2. 发送不明保留同一请求；持久化后A看到R1等待页，不能替B确认。
3. B从自己的待办读取同一R1，接受、拒绝或修改。接受需当前角色、资格、placement和proposal版本均有效。
4. B修改为R2时展示差异，并成为R2发起方；A作为R2接收方重新明确确认，不能复用R1同意。
5. 过时版本、撤回、过期、角色／资格变化返回冲突或受限状态，不直接显示成功。撤回只允许本人尚未生效的提案。
6. 方案双方确认不等于宠物已接回；实际交接仍需双方独立确认，否认／失联／安全争议转协助，不靠超时结束。

所有事件保留原申请AD-DEMO-01对应的真实ID（设计中仅为示例）、placement、提案ID与版本。重新匹配仍受实际接回与新发布版本核对约束。

R1／R2仅是固定状态的评审数据，不是每次重提都重置的编号。拒绝、撤回或过期后重提读取最新基准并生成新的递增版本与提案ID；同一命令弱网重试沿用原幂等键，不能另建一份R1。已确认的安排与尚待确认的新提案仍分列，不能因新提案失败而清除原有效安排。

## LR05 对原回执追加

回执RP的“补充说明”进入append模式，显示原回执与允许范围，主按钮为提交到原回执。保留原报告、阶段与证据，追加有自己的请求键，不能调用create_report。

append_pending→appended / failed / credential_invalid。结果不明只查本次追加；成功返回同一RP进度。凭据过期／丢失／无权限先核对受限访问，不泄露他人工单，不能靠输入可猜编号恢复权限。恢复人工渠道未就绪时如实显示限制，不伪造受理。

## LR06 删除指定资料与账号注销

两个独立目的：
- delete_selected：选择字段／附件和排除范围→说明影响→本次身份核对→最终确认→提交结果→DR-PART进度；账号保留。
- close_account：展示整个账号影响与未完成事项→本次身份核对→最终确认→提交结果→DR-ACCOUNT进度；登录关联、照护交接、工单与必要记录分别处理。

身份核对产生短时、绑定本次用途和范围的凭据，不是受理申请。现有可用验证方式按账号能力展示，不强制手机号或先绑定邮箱；验证码也分用途，不借用登录／交流凭据。范围修改、会话切换和凭据过期使原核对失效。

最终页面重述账号、类型、所选范围、必要留存及备份，要求明确同意后才提交。最终提交前取消不创建请求。pending或unknown不显示“请求已收到”；仅持久化并返回对应回执后显示收到，收到不等于清理完成。

DR的补充／申诉保持原回执与类型，不进入普通新建安全报告。公开隐藏、主存清理、例外留存、导出／CDN和备份分别显示状态；正式期限仍依真实数据流及适用义务核定。

本轮验收分为：原生可编辑结构、实际Figma动作的目标与条件、当前截图、角色／用途／版本语义。任一链接存在都不能抵扣“目标操作正确”。真实API、核验通道、短信／邮件、工单、清理和设备运行仍需获授权接入与验证。

## 1. 设计结论

宠友圈是“朋友之间持续分享宠物日常”的关系流，不是新增一个短视频广场。公开社区负责发现内容，关注负责单向订阅，宠友圈负责双向确认后的交流，宠物主页负责每只宠物的资料与日记归档。它们共用内容和账号，但权限不能互相放大。

用户已要求“核心交互像朋友圈”，并在上一轮推荐双向好友后要求认真设计。本版以“双向确认、时间序、默认朋友可见”作为明确标注的推荐方案，不声称用户已逐条确认所有隐私细节。下面规则可整体评审；不变更真实用户设置。

视觉来源为已选 Friendly：Noto Sans SC／Manrope、轻浅中性底、珊瑚白字主按钮、真实猫咪照片优先。48 高／24 圆角真胶囊按钮，卡片和输入框 16 圆角，48×48 最小常规图标触控。猫、狗、其它宠物共用规则，照片与昵称必须匹配。不使用微信绿色、品牌图标或素材。

## 2. 四个入口的分工

| 入口 | 关系／主要排序 | 核心用途 |
|---|---|---|
| 推荐 | 公开内容；推荐规则另定 | 认识新宠友、发现内容 |
| 关注 | 单向关注 | 阅读主动订阅的公开日常，不自动成为朋友 |
| 宠友圈 | 双向确认；发布时间倒序 | 看朋友近况和互动；点赞不顶起旧帖 |
| 宠物主页 | 一宠一档；日记时间序 | 管理资料、图文成长记录与可选领养 |

社区顶部分别保留“推荐／关注／宠友圈／同城”，不挤占已有底部导航，不添加第六个 Tab。圈内提供“宠友／新朋友”和“写日常”；群聊从消息进入，圈子不是群消息流。我的页面提供自己的日记与圈权限入口。

每个用户可建立多只宠物，不设人为数量上限；上传频率／存储保护不等同于宠物数量限制。本轮聚焦圈子，不宣称完整多宠物管理已经制作。

## 3. 圈主页与动态卡

主页保持简洁：小幅宠物封面和简短引导即可，不用大海报压住内容。封面、身份和操作各自清楚，不用宠物照片作低对比文字背景。

单条动态的顺序为作者头像和昵称 → 时间／范围 → 正文 → 照片 → 喜欢／评论／更多 → 可见互动摘要。账号是操作主体，关联宠物是内容对象，不能把宠物名当成人的账号身份。点击作者进入对应主页，点击公开宠物标签进入对应宠物资料，点击照片进入同一动态的相册。

正文过长折叠为“展开全文”，展开后不跳页或丢滚动位置。单图按构图显示，不强行裁掉宠物；多图按原顺序排成稳定网格，最后一个单元可显示剩余数，查看器有上一张／下一张及返回。查看器不得混入另一只宠物的照片。首版不放视频、播放按钮或自动轮播。

喜欢和评论始终可发现，不全部藏在省略号中；更多承载不看TA、举报、自有内容权限与删除。互动区只显示当前有权读取的名字和计数。不展示虚构热度、“平台真实宠主”等无依据徽章。

## 4. 发布流程

写日常 → 选择照片 → 可选关联宠物 → 选择受众 → 预览实际公开内容 → 确认发布 → 返回圈子并定位新动态。

草稿保留文字、照片选择和范围；取消时明确“存草稿／放弃／继续编辑”，失败后不清空内容。上传中显示逐图进度和取消，失败图可重试／移除；发布按钮不能重复提交。离线稿不显示“已发布”。

关联宠物可选，允许纯文字，也不要求先填写完整宠物档案。位置默认“不显示”，不为了发日常申请 GPS；公开地点只到用户选择的粗粒度，不附带住宅或照片 EXIF 精确位置。首版采用静态图片与静态表情；照片张数、压缩参数和容量阈值在实施评审确定，不把视觉网格当成最终上传上限。

“公开到社区”是单独的受众选择与确认流程，不是叠加在“朋友可见”上的布尔开关。确认公开后，该内容具有公开受众，不能继续把它标成私密朋友内容。发送前预览明确标示这一变化。

## 5. 可见性：内容授权与资料授权分开

| 情况 | 对外行为 |
|---|---|
| 公开宠物资料＋朋友动态 | 资料按其公开范围访问，动态只给允许的朋友 |
| 公开宠物资料＋仅自己动态 | 不把私密日记作为公开主页的缩略图、计数或相册内容 |
| 私密宠物资料＋拟分享动态 | 明确选择仅分享本条图文，不能自动开放整份档案；关联标签对外不生成私密资料入口 |
| 仅自己动态 | 不进入圈子、公开社区、他人的搜索或通知预览 |

私密资料与公开单条内容的组合仍是待用户确认的产品决策。本版采用保守草案：关联私密宠物时保持日记私密；若用户主动改变内容受众，须明确确认“仅分享这条内容，不公开档案”，无隐式批量公开。未完成该确认前不发布。这不是未经授权改变真实数据。

受众互斥：朋友可见／仅自己／部分朋友／不给谁看／公开到社区。后两种选择器只展示当前可选宠友，排除自己与重复选择；确认页显示选择后的受众摘要。公开范围再确认，不预勾，不强迫公开换取功能。

调整为仅自己或删除后，信息流、详情、相册链接、互动通知、分享预览都重新鉴权；不能只隐藏卡片。历史锁屏通知及他人截图无法保证召回，设置说明应如实告知。不能通过反复查询计数或照片 URL 读取已收紧内容。

## 6. 好友关系与历史

朋友需要双方确认。关注不是好友；收到请求也不是已成为好友。首版通过站内公开主页／用户主动使用的邀请入口发起，不读取通讯录，不假设可以同步微信好友。

请求有发送、待处理、接受、暂不接受、撤回、不可用等状态；同一双方只保留一个待处理请求，频率控制不依赖 UI 倒计时。接受前显示必要公开资料和申请理由，不索要地址、身份证或宠物核验原件。

建议新朋友默认只看成为朋友后的圈动态；不自动开放此前朋友内容。若未来加入历史开放功能，应由作者明确选择，不能把“同意好友”解释为公开全部旧日记。具体历史规则是评审默认，不冒充用户已确认。

移除朋友和拉黑分别说明影响并二次确认。移除后失去朋友受众内容访问，公开社区内容仍按公开规则处理；私聊是否继续由独立接收设置决定。拉黑还限制联系，不能因拉黑认定对方违规。好友列表默认不向公众展示。

## 7. 评论与回复

点击评论定位同一动态的输入区；回复明确显示“回复某人”与取消回复。提交前显示公开范围，不用私信样式误导用户以为评论只给对方。作者回复有角色标记，但不代表平台核验。

建议采用共同好友可见：作者可看自己动态下的有效互动；其他人只能看作者、自己，以及与自己也为朋友的评论者。所有情况先满足动态访问权限。回复继承被回复评论的可见约束，隐藏的父评论不能经引用、昵称、头像或通知泄露。计数按可见互动计算。

普通用户可删除自己的评论，举报他人评论；作者可处理骚扰但不能无记录地改写他人发言。删除显示清楚结果，回复目标不存在时保留输入并提示重新选择，不误回复到另一人。内容审核与举报回执独立，不按举报票数自动认定违规。

## 8. 全站共用表达能力

统一面板服务帖子、日记、评论／回复、领养交流、私信和群聊；不是每个地方重新设计一套。

快捷表态与发送内容分开：一人对一条内容最多保留一个当前表态，可更换／取消，不因连续点按增加人数。首版可用喜欢、开心、抱抱、鼓励等稳定集合。既有喜欢控件默认爱心，长按不是唯一入口，更多表态有可见的点按入口。

发送面板提供 Unicode 表情与平台静态表情包，选择后先进入待发送状态，不自动发送；文本可插入光标位置，静态图片表情独立作为消息／评论内容。没有资产或授权时不伪造品牌表情包；设计只展示有来源的内容，后续统一资产再交付。

表情有文字名称和选中状态说明；读屏不能只听到未命名图像。不靠颜色表示已喜欢。键盘可打开／关闭面板和返回输入，系统减少动态偏好不影响功能。GIF、动图、视频表情均不在首版。

## 9. 冷启动、失败与边界

| 状态 | 设计处理 |
|---|---|
| 尚无好友 | 真空态；写自己的日记、去公开社区认识宠友、主动发起请求；不造假好友或互动 |
| 有好友但没有动态 | 告知暂无新日常，不暗示朋友删除了你 |
| 原帖无权查看／已删除 | 中性提示与返回，不保留私密缩略图，不泄露是拉黑还是范围排除 |
| 相册取消／权限拒绝 | 可继续写文字和存草稿，不循环弹权限 |
| 图片失败／断网 | 保留草稿和成功选择的图，明确重试和移除 |
| 评论中权限被收紧 | 不提交、不丢本地输入，解释内容暂不可访问 |
| 内容待审核 | 仅作者看见真实状态，不给他人制造已发出的推送 |
| 好友请求受限 | 给出可理解的等待／撤回路径，不无限重发打扰 |

首发武汉／上海和走失提醒是独立能力，不自动把走失警报或交易广告塞入每个人的宠友圈。用户可主动分享有访问权的领养／互助卡；卡片分享不增加查看私密材料的权限。

## 10. 页面与验证范围

22 个场景的设计清单见 pet-friends-circle-screens.json。当前四屏视觉提案只覆盖主线样貌，不把清单数量当作原生页面完成数量。后续必须原生组件化、连通正常与异常路径后，才计入可交互原型。

验收至少覆盖：无朋友的真实空态；好友双方确认；新好友看不到未授权旧内容；同一内容从圈子／宠物主页读取同一受众；私密宠物公开单条前的确认；朋友→仅自己后旧通知与图片失效；评论共同好友与引用不泄露；爱心更换不重复计数；照片取消／失败不丢草稿；自己删除与他人举报分开；猫狗照片和身份一致；48px触控、320宽与大字体、对比度、键盘及读屏检查。
